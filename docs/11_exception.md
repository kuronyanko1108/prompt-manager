# 例外処理設計書

## 1. 目的

本ドキュメントは、発生時の適切な処理方法を定めることで、システムの信頼性向上と開発効率の最大化を目的とする。

## 2. 適用範囲

- Repository層
- Mapper層
- Service層
- Controller層
- Ui層

## 3. 用語定義

| 用語              | 定義                                                                           |
| ----------------- | ------------------------------------------------------------------------------ |
| 例外（Exception） | プログラム実行中に発生する、通常の処理では対応できない異常状態。               |
| Repository層      | データベースなど永続化層へのアクセスを担当する層。                             |
| Mapper層          | データベースやユーザー入力データの変換を担当する層。                           |
| Service層         | 業務ロジックを担い、データの取得・加工や他層への処理委譲を行う層。             |
| Controller層      | UI層からの入力を受けてサービス層に処理を委譲し、結果をUI層に返す役割を持つ層。 |
| UI層              | 画面表示やユーザー操作の受付など、ユーザーとのやり取りを担当する層。           |
| 業務例外          | 業務ロジック上で発生する想定内の例外。                                         |
| システム例外      | システム障害や予期しないエラーなど、想定外の例外。                             |
| 伝播              | 発生した例外を上位の層へ引き継ぐこと。                                         |
| エラーメッセージ  | ユーザーまたは開発者に通知するエラー内容の文言。                               |

## 4. 例外クラス設計

- 4.1 継承構造

```text
Exception
└──AppException
    ├──SystemException
    │   └── DatabaseException
    └──BusinessException
        ├── ValidationException
        └── PromptException
```

- 4.2 各例外クラスの役割
  | クラス名 | 説明 |
  |----------------------|--------------------------|
  | └──AppException | アプリケーション共通例外 |
  | SystemException | システム例外 |
  | BusinessException | 業務例外 |
  | database_exception | データベース関連例外 |
  | ValidationException | 入力値チェックによる例外 |
  | prompt_exception | プロンプト操作例外 |

## 5. 各レイヤーでの例外処理方針

### 5.1 Repository層

- DBアクセス時のエラー（接続失敗・クエリ失敗など）は`database_exception`としてraiseする
- 想定外の例外は`app_exception`でラップしてraise
- 原則としてcatchせず、上位層（Mapper/Service）に伝播

### 5.2 Mapper層

- データ変換時の不整合（型不一致・必須値欠損など）は`prompt_exception`としてraiseする
- Repository層からの例外はcatchせず、そのまま伝播

### 5.3 Service層

- 業務ロジック上の異常（バリデーション失敗など）は`prompt_exception`としてraiseする
- Repository/Mapper層からの例外はcatchせず、必要に応じてメッセージを加工して伝播

### 5.4 Controller層

- 下位層（Service等）からの例外をcatchし、UI層に返すエラーメッセージやレスポンス形式に変換する
- 想定外の例外はログ出力し、ユーザーには汎用的なエラーメッセージを返す

### 5.5 UI層

- Controller層から受け取ったエラーメッセージをユーザーにスナックバーで表示する
- システム例外や想定外のエラーは、ユーザーに不安を与えないよう簡潔なメッセージで通知する
- エラー内容をログに出力する

## 6. 例外発生・伝播ルール

- 各層で発生した例外は、原則としてcatchせずにController層まで伝播させること。
- Controller層で例外を捕捉し、適切なエラーメッセージやレスポンス形式に変換してUI層へ返すこと。
- UI層では、受け取ったエラーメッセージをスナックバーでユーザーに分かりやすく表示すること。

## 8. ログ出力方針

- 例外発生時は、必ずエラー内容・発生箇所・スタックトレース等の詳細情報をログに出力すること。
- ログレベルは、状況に応じて以下を使い分ける。
  - DEBUG：開発・デバッグ用の詳細な情報
  - INFO：通常の操作記録や処理開始・終了など
  - WARNING：軽微な異常やリトライ可能なエラー
  - ERROR：業務例外やリカバリ可能なエラー
  - CRITICAL：システム例外や致命的な障害
- システム例外や予期しないエラーは、必ずERRORまたはCRITICALで記録し、運用監視で検知できるようにする。
- ログ出力は、各層で責任を持って行い、特にController層・Service層での例外捕捉時に詳細を記録すること。
- ログの出力先（ファイル、標準出力、外部サービス等）は運用要件に応じて設定する。
- ログフォーマットは一貫性を持たせ、時刻・レベル・発生箇所・メッセージを必ず含めること。
